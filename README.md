## 一、先把"丢包"拆开：mkcloud 端内、海外段、国内接入是三码事

很多搜「mkcloud 丢包」的用户，最后拿到手的其实是一条混合链路：

1. 国内入口端（你本地到 VPS 的入口 IP，通常绑定某个省的白名单）
2. 国内跨境段（云厂内网/八线 BGP/IX 出口）
3. 跨境物理段（光纤、海缆、IEPL 或 IPLC 的国际段）
4. 海外落地段（VPS 出口 IP 到目标业务服务器）

Mkcloud 在知识库里反复强调一句被引用很多次的话：「专线不代表整条光纤归单个用户独占，也不代表自动加密、永不丢包或所有业务都适合。」这句话其实就是在告诉用户：哪怕买的是 IEPL/IPLC，丢包依然是分段的，不能看到"专线"两个字就默认全程零丢包。

第三方测评在 mkcloud 广港 IEPL 上的实测口径大致是：正常时段基本 0 丢包，晚高峰能控制在 1% 以内；Mkcloud 自己也把"端内延迟"作为产品资料发布，比如广港 1~2ms、沪港 21ms、沪日 25~28ms、沪美 124~134ms——这些数字仅指 VPS 出口到目标 IX 的端内参考，而不是从你本地到亚马逊、Stripe、华泰接口的全程表现。

结论是：讨论 mkcloud 丢包，必须先说清楚是"哪一段"。

## 二、Mkcloud 各线路在丢包上到底表现如何（按方向拆开）

下面是按官方知识库口径 + 已能找到的第三方测评整理出的对比，不是全程到目标的实测，只是端内/产品端参考。

### 1. 广港 IEPL（华南→香港）

- **端内延迟**：1~2 ms
- **类型**：IEPL（物理专线，跨境的物理段独占性比 IPLC 更接近"运营商级物理通道"）
- **丢包特点**：在已公开的测评里，被多次描述为"基本 0 丢包，晚高峰 1% 以内"。这是几条线里丢包最稳的之一，因为广州到香港物理距离短、海缆单一，IEPL 段相对干净。
- **适合谁**：华南办公、跨境电商香港节点、低延迟要求高的游戏加速器节点、API 高频调用。

### 2. 深港 IX（深圳→香港）

- **端内延迟**：1~2 ms（依赖云前置）
- **类型**：IX（云厂接入的上云互联优化专线）
- **丢包特点**：IX 不是物理专线，丢包受云厂内网和香港 IX 出口拥塞影响。Mkcloud 自己也提醒："没有对应直达产品的地区，可测试香港或日本出口的后续访问，但不能写成新加坡、韩国等当地节点。"
- **入门价格最低**（月付 ¥158 起 + 云前置费），但对前置云的依赖让丢包稳定性比广港 IEPL 略差。

### 3. 沪港 IPLC / 九线（上海→香港）

- **端内延迟**：21 ms
- **类型**：IPLC（国际私有租赁线路）
- **丢包特点**：上海到香港是 IPLC 主流路径，端内延迟稳定。丢包主要来自上海九线入口的动态选择和晚高峰拥塞。官方提醒金融业务方向用此线路做实际接口测试，不要直接套用端内延迟。

### 4. 沪日 IPLC（上海→日本）

- **端内延迟**：25~28 ms
- **类型**：IPLC
- **丢包特点**：日本方向距离更远，海缆是太平洋段或走美日段。晚高峰风险比广港更大，但比沪美容易得多。适合 TikTok 日本区、游戏出海日本业务。

### 5. 沪美 IPLC（上海→美国）

- **端内延迟**：124~134 ms
- **类型**：IPLC
- **丢包特点**：太平洋海缆距离决定了基础延迟就高，IPLC 本身相对干净，但物理段拥塞、运营商路由切换、海缆故障都会反映在丢包上。测评里美国方向对国内移动网络格外敏感。
- **适合谁**：对延迟不敏感、流量以海外为主、对稳定性要求中等以上的业务。

### 6. 厦港、泉港高防

- **端内延迟**：参考港方向，但福建入口
- **类型**：含 DDoS 防护的港方向专线
- **丢包特点**：高防线路本来就有清洗策略，正常业务流量丢包极少，但要注意"业务高峰+攻击"叠加时的瞬时丢包。

## 三、影响丢包的真实变量（mkcloud 自己也反复提）

Mkcloud 在知识库里把"丢包相关的边界条件"讲得非常克制，下面这些是会影响实际丢包率的因素，也是和"端内延迟漂亮数字"不一样的层面。

- **单端双独立 IP 机制**：每台 VPS 配 1 个独立入口 IP 和 1 个独立出口 IP。你从国内入口，流量在 VPS 内走业务后从独立出口发出。这种架构的好处是入口和出口解耦，入口段丢包不会拖垮出口端；但代价是"入口 IP 的网络质量"完全取决于你所在的省份/运营商，没有全国统一的 SLA。
- **直连款绑定省份**：直连类产品绑定一个连入省份，绑定可切换。这意味着同一个套餐，从移动、电信、联通不同入口看到的丢包表现可能差异很大。
- **IX 依赖云前置**：深度 IX 类型产品需要香港/日本/美国方向的云前置机器，前置云本身的网络抖动会反映成你的"丢包"。
- **共享带宽是峰值**：Mkcloud 明确写着"共享带宽为峰值，不保证持续跑满"。所以晚高峰丢包+抖动往往不是"断线"，而是共享池被打满后的带宽衰减表现。
- **独享不代表整条路径**：独享带宽也不代表计算资源或整条物理路径独占，独享是"在你和上游之间"独占承诺，不代表跨境段独占。
- **默认无 SLA**：Mkcloud 标准产品默认无 SLA 条款，需要书面承诺要单独走工单/合同。
- **流量双向上下行统计**：超量后会暂停服务，自助购流量重置或工单补差价升级。这点和一些机场"按月宽容"逻辑不同，对流量敏感业务有直接影响。

把这几条拼起来，搜「mkcloud 丢包」得到的"零丢包/晚高峰丢包 1%"应该理解为：**在端内通道、官方推荐入口、共享带宽未打满、网络空闲时段** 的近端表现。真实业务下还可能被本地移动/电信网络、目标服务器的限速策略放大。

## 四、自己测一份 mkcloud 丢包：用什么工具、看什么数

如果你已经买了或者准备买 mkcloud，先不要相信营销页的"端内延迟"，自己测一遍更稳。下面是 mkcloud 知识库给出过的、可执行的步骤。

1. **拿到入口 IP + 出口 IP 后，分别跑 ping -t 200+ 个包**
   - 入口 IP 看的是"你本地到出口入口"的网络。
   - 出口 IP 看的是"从 VPS 内往目标"的网络。
   - 关注丢包率、平均延迟、波动区间，而不是单次最低值。
2. **在 VPS 内跑 iperf3 到目标业务服务器**
   - 注意需要目标端授权部署 iperf3。
   - Mkcloud 提醒：持续满载可能消耗大量流量并影响业务，不要默认测 48~72 小时。
3. **用 curl/wget 跑业务请求，记录超时、重连、成功率**
   - 金融/支付类业务建议记录 p95/p99 长尾延迟，而不是平均延迟。
   - 没有完整日志时不要写"具体成绩"，因为没用。
4. **跨高峰/非高峰对比**
   - 至少比较 14:00、20:00、22:00 三个时段的丢包率。
   - 如果某个时段明显劣化，先确认是不是共享带宽被占用，再决定要不要升级套餐。
5. **不同入口省份测一遍**
   - 因为直连款绑定省份，万一你用的运营商在该省入口拥塞，工单改绑定省份换条线，可能比"换套餐"更便宜。

**判断标准**（一个比较通用的参考，不是 mkcloud 自己写的）：
- **丢包率 < 0.5%**：端内基本可以接受。
- **0.5%~1%**：晚高峰可能反复出现，业务侧需要做重试。
- **>1% 持续出现**：在没有外部故障的前提下，建议提工单测试，或考虑换套餐/换线路。

这套标准引用的是常识范围，mkcloud 没在知识库里给出官方"合格丢包率标准"，因为按官方说法："延迟与业务成功率另行测量"。

## 八、最后几条买之前要知道的事

1. **Mkcloud 明确不是机场**：官网把"机场、翻墙回国"列为禁止用途，所有专线走省级白名单，只允许单一省份 IP 连入。如果你只想要个便宜 VPN，这个产品定位就错了。
2. **丢包别光看端内延迟**：端内 1~2ms 是 VPS 出口到 IX 的参考值，从你本地到目标业务的真实丢包取决于入口省份、目标服务、本地运营商、晚高峰四个变量。
3. **慎用"晚高峰 1% 以内"这种说法**：那是已公开测评的近似值，不是 mkcloud 官方对所有用户的承诺，且不同时段/入口会有波动。
4. **独享 ≠ 全路径独占**：买之前不要把"5M 独享"理解成"国际段独占"，mkcloud 自己也没这么宣传。
5. **降档差价不退**：升降级都需要工单操作，降级至更低价格时差价不退。
6. **默认无 SLA**：金融、支付、量化等需要 SLA 的业务，必须工单单独谈，不能默认。
7. **客服高峰慢**：在线客服响应可能慢，mkcloud 自己推荐"技术问题直接提工单"，通常比在线客服处理更快。
